# Threat model — initial Phase 0

## Assets and trust boundaries
Protected assets: currency, inventory, store/build ownership, upgrade state, shift rewards, persistent profile, purchase fulfillment, moderation and service availability. Clients and all client-originated values are untrusted. Roblox platform services and server code are trusted within their documented behavior. External assets/packages are untrusted until provenance and code review are complete.

## Abuse cases and controls
| Threat | Example | Required control |
|---|---|---|
| Currency manipulation | Forged sale/reward or client-supplied price | Server calculates from catalog and valid state; atomic transaction |
| Remote abuse | Invalid types, huge payloads, floods | Strict schemas/size caps, per-player rate limits, bounded work and safe failure |
| Ownership bypass | Build/checkout against another store | Resolve owner and role server-side on every action |
| Inventory duplication | Replayed stock/checkout request | State transition checks and idempotency/transaction IDs |
| Purchase replay | Repeated receipt callback | Server-side receipt verification and durable idempotent fulfillment |
| Persistence corruption | Old/concurrent write overwrites new data | Versioned schema, serialized/session-coordinated updates, backups/recovery procedure |
| Permission escalation | Client selects manager role | Server-owned role assignment and explicit allowlist |
| Resource exhaustion | Spawn/pathfinding/event spam | Server caps, cooldowns, bounded NPC populations and task queues |
| Unsafe admin tooling | Exposed command or debug remote | No public admin remote; restricted, audited development-only tools |
| Malicious dependency/asset | Toolbox script exfiltration/backdoor | Original or reviewed assets only; provenance and source review |

## Remote validation checklist
Validate type, finite numeric values, bounds, identifier allowlist, serialized size, ownership, permission, distance where relevant, current state, cooldown, and duplicate/replay status on server. Never accept client authority for cost, reward, entitlement, target owner, or transaction outcome. Rejection is cheap, non-mutating, and does not leak sensitive data.

## Release-blocking security tests
Forged requests, malformed and out-of-range values, cross-player ownership, duplicate/replay transactions, request floods, concurrent operations, persistence failure/recovery, and purchase reconciliation. Any defect affecting currency, ownership, purchases, or persistent progress blocks release.

## Phase 0 limits
This is a design threat model, not a security audit. No runtime code or adversarial tests exist yet. Reassess when remotes, persistence, co-op roles and commerce are designed; verify current Roblox security and commerce documentation then.
# Phase 3/4 additions
- Join requests are rate-limited by the server. Only the current store owner can assign roles or remove a player; role names are allow-listed and target users must be in the same server.
- Every ProximityPrompt remains a client-controlled signal. The server rechecks membership, role/action permission, owner profile lock, world ancestry, character distance, player membership and interaction rate before changing shared state.
- Member lists are generated on the server from current Players and safe display fields. Clients never submit a balance, profile, stage, inventory count or saved employee value.
- A cashier purchase is checked and charged by the server. Automatic checkout uses the existing economy transition and is delayed, bounded to the Checkout stage, and rechecked against owner/save state.
- Persistent profile access is allow-listed to the user-provided development universe ID. Other universes run session-only; production is not configured.
- Profile schema versions are checked as finite, bounded integers. Read-only visitors receive zeroed economic counters in replicated state; only store owner and approved helpers receive the shared operational totals.
- Funnel telemetry is development-universe-only and wrapped so AnalyticsService failure cannot block gameplay. Roblox associates events with its required Player argument; the game adds no custom fields or identifiers. The temporary funnel-session GUID stays in server memory and is not stored in the player profile.
- The checkout spill is activated only by the server sale transition. Cleanup has a fixed server-defined reward and requires Owner/Manager or Maintenance, the active `Spill` stage, prompt proximity and the common interaction cooldown. The client cannot choose the event, reward, amount or resume stage; the saved stage is schema-validated.
- Customer count is capped at three and reconstructed from saved sales. Waypoints, queue recovery, checkout readiness and exit state are server-owned presentation; no NPC model, animation callback, client prompt payload or customer attribute changes money or inventory.
- Cleaner hiring checks completed-shift eligibility, owner/Manager permission and server-defined price. Its delayed cleanup rechecks owner profile lock, hired state and active `Spill` stage, and calls `Economy.cleanSpill`; races with a player cannot pay twice because the first transition clears the active stage.
- Multi-product actions accept no client-selected quantity or price. The server allow-lists Citrus Pop/Berry Bites, charges catalog prices, checks warehouse ownership, role and prompt range, caps Berry Bites shelf/backroom inventory, and allows one pending shipment. Profile schema v7 validates SKU counters and migrates an untagged pending shipment as Citrus Pop. Owner/Manager can order; Stocker can stock Berry Bites. Unauthorized, invalid, duplicate, early, or capacity-rejected actions do not mutate inventory or cash.
- The Chaos Director derives the spill/outage plan from the server-known owner ID and validated completed-shift count. A Power Outage may follow the first or second server-approved sale. The persisted `PowerOutage` stage and bounded server timestamp control the event; only Owner, Manager or Maintenance can use the breaker. Manual recovery clears the deadline, and automatic recovery rechecks stage, timestamp and profile lock. Replayed or stale prompt attempts do not grant a reward or alter sales. The profile validator rejects inconsistent stage/deadline/sale states; a lock loss prevents automated mutation.
- Customer Rush starts after the third approved sale only when two shelf units remain. The server caps the queue at five, controls its 60-second deadline, catalog-priced extra sales, and one-time `$20` completion reward. Timeout clears the bonus queue without a penalty. Profile schema v9 pairs `CustomerRush` only with its deadline; expired, duplicate, late or unauthorized sales cannot earn the completion bonus. Cashier automation reuses the same sale transaction and pauses after timeout.
- Weighted customer preferences are selected and fulfilled on the server from the validated completed-shift count, sale number, live stock, and server prices. Clients receive display strings only; they cannot choose basket products, quantities, or totals. See `operations/PHASE30_CUSTOMER_PREFERENCES.md`.
- The Chaos Director derives each shift's bounded spill/outage schedule from the owner ID and validated completed-shift count. Clients cannot select events or timing; active event stages/deadlines are checked and saved through the existing profile path. See `operations/PHASE31_CHAOS_DIRECTOR.md`.
- Retail layout proposals are limited to four server-allow-listed product IDs, finite two-stud grid coordinates, 0/90 rotations, store-floor bounds and collision clearance. The server requires Owner/Manager, Complete stage, station range and a ready profile save before moving or persisting a shelf. See `operations/PHASE32_RETAIL_LAYOUT.md`.
- Customer satisfaction is changed only by a successful server checkout transaction and clamped to 0–100. Profile normalization rejects malformed scores; snapshots expose the score only to authorized store members. A client cannot submit a rating, fulfillment result or delta. See `operations/PHASE33_CUSTOMER_SATISFACTION.md`.
- Customer baskets are derived and priced on the server from shift sales and available inventory. The client supplies no product, quantity, basket or price. All basket stock deductions and revenue credits occur within one `sellProduct` transition; customer count advances once per basket. Empty-stock and stale checkout attempts are non-mutating. Display labels and route animations do not grant sales.
- Storefront palette purchase is Owner/Manager-only through the common prompt gate. The server checks stage, balance, existing ownership, range, profile lock and rate limit; it fixes the `$180` cost and preset, saves one boolean, and applies only fixed server-defined colors. Client input cannot choose color, cost or ownership. Profile schema v10 migrates older profiles to the original palette.
- Customer reaction labels are derived from the server's current stage and are presentation-only. They cannot mutate queue count or pass checkout; queue recovery restores labels from current server stage.
- Golden Apples use the server catalog for `$12` sale, `$35` order, 18-unit shipment, three-unit restock and 24-unit shelf cap. Profile schema v11 bounds shelf/backroom values, requires warehouse ownership for apple stock, and allow-lists the shipment SKU. Stock, order, receive and checkout prompts use the same server role/range/cooldown/save checks. No client-supplied SKU, price, or quantity is accepted.
- Employee automation toggles use separate fixed action IDs for cashier, stocker and cleaner; they accept no client-selected profile field. The server requires Owner/Manager, an existing hire, valid prompt range, request cooldown and a ready profile lease. Schema v12 requires booleans and defaults absent legacy fields to enabled. Delayed actions recheck the automation flag and lease immediately before calling the existing server economy transition; generation tokens invalidate stale scheduled work.
- Storefront preview is a fixed, non-persisted palette controlled by an Owner/Manager prompt through the common role/range/cooldown/save gate. The client supplies no colors or purchase values. Preview cannot change cash or ownership; the separate purchase still uses the fixed `$180` server transaction and existing saved upgrade flag.
- Delivery-worker hiring is Owner/Manager-only, warehouse-gated, completed-shift-only and server-priced. Auto-receipt accepts no client SKU or quantity; a delayed callback rechecks a captured shipment timestamp, automation state and profile lease before the same bounded receipt transaction used by manual dock interaction. Generation tokens cancel stale pickup timers.
- Sunrise Cereal actions accept no client SKU, price, basket size or quantity. The server fixes `$16` retail, `$45` for 18-box wholesale, three-box restock and 24-box shelf cap. Profile schema v14 bounds shelf/backstock and allow-lists the shipment SKU; stock/order/receive/sale use the existing role, prompt-range, cooldown, warehouse and save-lock checks.
- Price prompts bind to a fixed server product ID and cycle through three exact server-derived values; clients cannot choose a price or product. Profile schema v15 rejects unknown SKUs and unsupported prices. Checkout recalculates each basket with the current server price after role, range, cooldown and profile lease checks.
- Price-sensitive basket quantities are derived only from server sales progress, saved prices and shelf stock. Discounts can add at most one unit to a single-product basket; premium prices can remove at most one unit from a multi-unit request. The checkout transition recomputes quantities and totals and applies them atomically.
- Stocker automation accepts no client SKU or quantity. It inspects the current server basket intent and delegates to the existing per-SKU restock transitions after rechecking stage, employee state, owner readiness, save lease and generation token. Citrus Pop and profile shelf counts are capped at 24; other SKUs retain their existing limits.
- Customer Assistant hiring uses a fixed server cost, completed-shift gate, Owner/Manager role, prompt range, rate limit, owner readiness and profile lease. Schema v16 accepts only a boolean hire flag. The assistant changes a fixed customer browsing tween duration only; it cannot modify basket contents, customer count, checkout readiness or economy state.
- Repeat-shift analytics are emitted only by server-confirmed shift/profile milestones in the development universe. Funnel UUIDs stay in server memory, and no client remote or game-owned player/economy fields are included. AnalyticsService calls are protected so failures do not affect gameplay or persistence.
- Household aisle expansion uses a fixed prompt action, server-owned `$220` price, owner/Manager role, completed-shift gate, first-shelf prerequisite, common range/cooldown/profile-lock checks and a persisted boolean. The server constructs the shelf at one fixed location; clients cannot submit target part, model, transform or price. Schema v17 rejects malformed flags and expansion ownership without its prerequisite.
- Payroll rates are constants in the server `Economy` module and are summed from validated server hire state. Only the guarded close-shift transaction can charge payroll; pause toggles do not affect employment. The client receives a computed display total only for store members and cannot set rates, charge amount or closeout state.
- Warehouse layout requests are untrusted RemoteEvent payloads. The server checks Owner/Manager membership, Complete stage, warehouse ownership, profile lease, prompt range, cooldown, exact action, server-generated fixture ID, finite/grid coordinates, allowed rotation, collision, maximum fixture count and server price/refund before changing the layout. The client never sends Instances, costs, model names, ownership or a saved layout array. Schema v18 accepts only bounded shelf records and rejects layouts without warehouse ownership.
- Storefront palette selection is driven by fixed ProximityPrompt actions and a server-owned three-ID cycle. `Economy` independently checks the selected ID against its preset allowlist; profile normalization rejects unknown values and maps a legacy purchased style to Coastal Market. Preview state is not persisted or client-controlled.
- The freezer purchase accepts no client price, fixture position, SKU quantity or ownership value. `Economy` checks completed-shift stage, rear-wing/warehouse/bakery prerequisites, balance and retail-layout compatibility before mutation. Stock, price and shipment prompts remain fixed server-created objects; every transaction checks role/range/cooldown/save lock and catalog ownership. Profile normalization caps shelf/backstock, validates price/shipment IDs and rejects freezer ownership or stock without prerequisites.
- Warehouse and retail layout remotes consume a per-player cooldown before checking payload type or action. Requests received during cooldown receive no reply, bounding rejection amplification. Action-specific schemas accept only known top-level keys (maximum five), while existing server-owned role, proximity, grid, rotation, collision and persistence checks remain authoritative. See `operations/PHASE42_LAYOUT_REMOTE_HARDENING.md`.
- Self-checkout is a fixed server-created prompt gated by the same Owner/Manager or Cashier role, prompt distance, interaction cooldown, current-front-customer readiness and profile save lock as staffed checkout. The client cannot select lane, basket, item, quantity, price or reward; both actions call the same sale transition and the server enables only the lane assigned to the active customer. Profile schema v26 rejects self-checkout ownership unless rear-wing and warehouse prerequisites are owned. See `operations/PHASE43_SELF_CHECKOUT.md`.
- Phase 44 online order packing accepts no client-selected product, quantity or value. The server derives the next basket from a saved counter, rechecks stage/warehouse/stock, and consumes backstock before crediting current catalog prices. Manager and Stocker access uses common role, prompt distance, cadence, save-lock and transaction-lock checks. Failed readiness or authorization leaves money and inventory unchanged; see `operations/PHASE44_ONLINE_GROCERY_ORDERS.md`.
- Phase 45 delivery-worker automation has no client trigger or client-selected order. It requires a hired worker, enabled automation, completed-shift state, warehouse ownership, sufficient stock, a current profile lease and a shift marker not yet consumed. Generation tokens cancel stale callbacks; a shared transaction lock serializes employee and player fulfillment. Schema v28 validates the saved marker as a bounded integer.
- Phase 46 Customer Rush eligibility still checks server stock after the regular queue. The server owns the 90-second deadline, six-customer cap and `$30` reward; saved sales/deadline validation rejects impossible rush progress. Player checkout cannot extend the deadline or set the reward. Lane prompts remain limited to the assigned front customer.
- Phase 47 café transactions accept no client costs, quantities, or ownership flags. `Economy` independently checks warehouse/completed-shift prerequisites, cash, stock and capacity. Build, restock and serving use fixed server prompts with role/range/rate/profile-lock checks and one shared transaction lock. Profile schema v29 rejects café state without ownership, warehouse prerequisites, or within stock bounds.
- Phase 48 restaurant actions accept no client costs, meal quantities or ownership flags. The server checks café ownership, completed-shift stage, cash, capacity and stock. Owner/Manager build, Stocker prep and Cashier serve use common prompt role/range/rate/profile-lock checks and the shared transaction lock. Profile schema v30 rejects restaurant ownership without the café or meal stock/sales without restaurant ownership.
- Phase 49 electronics actions accept no client costs, quantities, stock or ownership flags. Server checks restaurant ownership, completed-shift build/restock stage, cash, capacity and inventory. Owner/Manager build, Stocker restock and Cashier sale use common prompt role/range/rate/profile-lock checks and the shared transaction lock. Profile schema v31 rejects electronics ownership without the restaurant or stock/sales without electronics ownership.
- Phase 50 garden actions accept no client costs, quantities, stock or ownership flags. Server checks electronics-store ownership, completed-shift build/restock stage, cash, capacity and inventory. Owner/Manager build, Stocker restock and Cashier sale use common prompt role/range/rate/profile-lock checks and the shared transaction lock. Profile schema v32 rejects garden ownership without Pixel & Plug or stock/sales without garden ownership.
- Phase 51 accepts only server-cycled style IDs (`coastal`, `urban`, `harvest`); no client color, part or model inputs exist. Purchase checks the completed-shift stage, garden-store prerequisite, remaining cash and one-time ownership. Owner/Manager role, prompt distance/rate and profile-save lock protect both prompts. Profile schema v33 rejects unknown styles or customization without Little Sprout ownership.
- Phase 52 visitors are server-created, anchored and limited to four models; clients cannot spawn, redirect or edit them. Their route targets derive only from server-owned business flags. Visitor movement has no economy or persistence authority, and route loops exit when the world is destroyed.
- Phase 53 purchase triggers originate only from the server's `BindableEvent` on completed visitor routes. `ShiftService` validates a fixed business ID, owner/profile readiness and lease/save state, enforces a 15-second per-business throttle, and uses the shared transaction lock. It passes no client prices, products or quantities; existing `Economy` methods validate stock/ownership and atomically update cash/inventory/sales.
- Phase 54 fleet purchase accepts no client cost or capacity. Server checks completed-shift stage, warehouse, hired worker, funds and one-time ownership. Automated orders recheck owner lease/save state, worker toggle, shift ID, bounded order count, deterministic order readiness and stock under the shared transaction lock. Schema v34 caps the per-shift count at three and requires fleet ownership to have warehouse/worker prerequisites.
- Phase 55 distribution-center purchase accepts no client cost or capacity. The server requires a completed shift, delivery fleet, available funds and no existing center under the shared transaction lock. Delivery ordering and receiving independently use the owned-upgrade-derived capacity; schema v35 rejects inventories above 500 without the facility and above 1,000 even with it, and rejects center ownership without the fleet.
- Phase 56 supplier-contract purchase accepts no client price, percentage or ownership flag. The server requires a completed shift, distribution-center ownership, sufficient cash and no current contract. `Economy.getDeliveryCost` computes every order charge; the UI only mirrors that fixed value. Schema v36 rejects a partnership without its distribution-center prerequisite.
- Phase 57 multi-store design: a location identifier from a client is an untrusted selector and must resolve to a server-owned runtime the player is authorized to use. Never accept UserId, profile key, cash, inventory or upgrade records as location state. Store membership and roles must be checked per location, while the DataStore lease and serialized write lock remain per owner profile. Verify isolation and save races with two locations before release.
- Phase 58 scenery is built from server-created parts. Phase 59 adds explicit florist action IDs and a server-created visitor event; prompt binds enforce role, distance, rate, profile readiness and the shared transaction lock. Visitor events accept only the fixed `florist` business ID and use server-owned price/stock. The bookshop shell remains scenery.
- Phase 59 schema v38 validates florist ownership prerequisite, stock cap and the requirement that stock/sales have florist ownership. The v37 location snapshot migration accepts the exact prior snapshot shape with only the newly added florist fields absent.
- Phase 60 location storage allows only the fixed `neighborhood` and `uptown` IDs. Reads return copies; writes require an existing ID and use the profile lease/save lock. Stored `uptown` data must normalize exactly through the established profile validators; the client cannot submit location records or select a DataStore key. No runtime should use this API until its balance source is synchronized with the root company balance.
- Staffed checkout, self-checkout and cashier automation share a server sale-in-progress lock held through the profile save and queue refresh. This prevents different authorized players or the employee from racing separate prompts against one visible customer while the save operation yields.
